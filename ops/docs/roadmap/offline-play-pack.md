# Offline play pack

In a production build, choose **Play offline → Download play pack** to save the build's public play shell and assets. The download size depends on the build and included collections. **Offline ready** means that the pack has been verified and saved; browser storage may later be cleared or evicted. The same control opens the dedicated offline studio and can refresh its download after an app update.

The offline studio reuses `GameBoard` for catalog games whose Local mode is enabled, with rules/guide data, native 2D pieces, themes, local bots and Stockfish JavaScript/WASM. Bot mode remains subject to each game's capability gate. Native 3D families cover Western chess, Khmer chess, Shogi/Mini Shogi, Xiangqi, Janggi, Makruk, draughts, Konane, Shatranj, Chaturanga and Jungle; available collections and their assets come from the matching build. Cambodia retains its local preview gate. Game switching makes a document navigation to the cached shell, without depending on an uncached Next.js RSC request. Friend, matchmaking and spectator controls are unavailable in this studio. Opening a friend URL offline offers a fresh local board without carrying its room ID or credentials into the offline URL.

## Build and cache contract

- `npm run build` generates the static `/offline` shell, then runs `prepare:offline`. `npm run cf:build` does the same before OpenNext copies public assets. The generated `public/offline-pack.json` is ignored by Git and must be deployed with the matching build. Development mode does not register the service worker or advertise downloads.
- The manifest contains public Next.js JavaScript/CSS/font assets, the shell, models, icons, and Stockfish. Each file has a byte count and SHA-256 digest. No account or play-page HTML is stored. Static application code for other routes may be included; it contains no server-supplied account data.
- The verified manifest's declared size is limited to 88 MiB (92,274,688 bytes). The former 80 MiB limit was insufficient once the previous build's assets plus the finished Celadon images and optimized model totalled 87,544,987 bytes (about 83.49 MiB). The bounded increase leaves room for rebuilt application chunks. This is a staged measurement before the next production build; its generated manifest will establish the final size, and download validation is still pending.
- The service worker fetches download files without credentials, checks an asset-path allowlist, verifies their contents, and only then switches the saved-pack pointer. Concurrent download buttons share one job. Interrupted or corrupt updates leave the previous complete pack available. One previous version is retained for already-open boards.
- Ordinary page requests remain network-first. On a failed document navigation, a complete pack redirects to the offline studio; without a pack, the small reconnect page is shown. API calls, room actions, account responses, and RSC payloads are never cached or replayed.
- Cached static assets support deployment query parameters and remain available when an older build chunk returns 404 after a deployment. Browser storage eviction clears the ready status on the next check. Cache storage is not a guaranteed permanent download; this follows the [service-worker offline application pattern documented by MDN](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Guides/Offline_and_background_operation).

## Original milestone evidence and validation scope

The following records describe the original offline implementation and its early continuations. Their game, collection, asset and test counts describe those builds, not the current pack or validation of later collections.

The original worker suite had eight tests exercising actual handlers: verified downloads, cold navigation, query-bearing static assets, stripped room credentials, corrupt-update recovery, account/API exclusions, three path-traversal forms, eviction fallback and shared concurrent downloads.

That milestone's local production-build browser audit saved the pack in a persistent Chrome profile, closed the browser and relaunched it with networking disabled. It opened the 21 then-locally-playable games, made Cambodia's opening king leap, received a classic bot reply and loaded the two 3D sets available at that stage. Runtime errors were empty. Download menus and boards were checked at desktop, 390 and 320-pixel widths, including viewport bounds and Escape/focus restoration. Four desktop/mobile cases for moves, bot replies, board geometry and unboxed coordinates also passed. Audit helpers and screenshots are ignored under `output/playwright/`.

The local-save continuation added IndexedDB autosave and resume for local and bot matches, retaining timelines, clocks, settings and variant-specific rule state; clocks wait for Resume. Its local production-build cold-start audit restored a Cambodian counted ending in 3D and continued it offline, including undo/redo. See `local-match-saves.md`.

The subsequent Shogi milestone added a third portable 3D collection. That build contained 84 verified assets (22.5 MiB). A fresh persistent Chrome profile downloaded it, closed and reopened offline, restored a Shogi save with its 3D porcelain appearance, played a Gote reply, then opened Mini Shogi with a separate boxwood preference and made a 3D move. This was evidence for those original Shogi models and that build's game-specific appearance persistence. See `ops/assets/shogi/README.md`.

Account contacts, live friend games, rankings and server analysis require connectivity. These local browser records do not establish physical iOS/Android installation or deployed-host delivery. Those checks and broader offline localization remain separate work. Later collection packs require their own cold-offline checks.
